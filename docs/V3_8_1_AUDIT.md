# v3.8.1 PacketTunnel 竞态审计

## 证据

样本：`PacketTunnel-20260803090641.log`，Bilibili iOS 9.5.0，Shadowrocket
PacketTunnel。日志中的 Wi-Fi LQM 正常，慢速请求集中在 cosov 点播媒体链路：

- `09:06:44.510` cosov 媒体请求已经开始；PlayView 到 `09:06:44.515` 才开始，
  CDN 响应脚本在 `09:06:44.904` 完成；
- `09:06:59.433` PlayView 先开始，脚本在 `09:06:59.718` 完成，随后首个媒体请求
  直接使用完整 Akamai URL；
- `09:07:31.398` cosov 媒体与 PlayView 同时开始，脚本到 `09:07:31.741` 才完成；
- 逃逸的 cosov 音频/视频连接分别约 `3005 ms`、`3272 ms` 后关闭，App 才继续尝试
  Akamai；其间可见连续 Range 请求而 Akamai 连接空闲。

结论：v3.8.0 对**新播放响应**的 Akamai 冷启动提升有效，但无法追溯修改 App 已从
内存缓存或预加载队列发出的旧媒体 URL。这是响应处理与媒体起请求之间的竞态，不是
带宽不足、cron 未运行或响应重排错误。

## v3.8.1 修复

1. 播放响应处理完成前，把当前对象实际选中的完整服务端目标 URL 同步写入
   `BiliCDN.mediaRoutes.v9`。
2. 以 query-free media path、签名有效期、`trid`、`mid`、`oi`、`buvid`、网络档案
   和表示档案共同绑定，不允许跨对象、音视频、清晰度或签名身份复用。
3. Shadowrocket 增加一个 `requires-body=0`、2 秒上限的 `http-request` 脚本，只匹配
   已审核媒体主机上的点播 `/upgcxcode/` GET/HEAD。
4. 命中时逐字节使用已保存的完整目标 URL；不探测、不拼接 host、不复制来源签名，
   保留 Range、User-Agent 和其他请求头。
5. 状态最多 64 条，在签名到期前至少 30 秒或最长 2 小时清理。损坏、过期、固定/
   关闭模式、直播、非点播、POST、对象或档案不一致全部原地址放行。
6. 媒体 CDN 仍不加入 MITM；脚本只改请求 URL，不读取媒体分片响应体。

## 验收边界

自动化覆盖跨响应/请求运行时键一致、目标自有签名、Range/UA 保留、容量与过期、
错误状态故障开放、模块 matcher、生成物校验和及 Release 资产。真机应重点复测横屏、
竖屏、连续播放、历史/收藏入口、后台恢复、快速拖动与切清晰度。

某个媒体请求如果在 v9 尚未获得该对象记录前已经离开 Shadowrocket，脚本不能回溯
迁移已经建立的 socket；但同对象后续 Range/流水线请求会进入请求规则。曾由先前
播放响应填充的缓存/预加载对象则可从第一条新请求直接命中。
