# v3.13.0：播放卡顿、重试与快进稳定性修复

日期：2026-09-16。基线：v3.12.0 / `897b655`。

用户反馈：国际版问题更明显，CDN 使用默认设置；关闭模块后花屏和音画不同步消失，
但部分视频的原始网络线路仍较慢。本轮据此优先修复插件自身介入播放和候选选择的风险。
没有取得该设备的媒体请求抓包，因此不把代码复现等同于某次设备解码故障的完整归因。

## 从所提供脚本学到了什么

参考用户提供的 **Bilibili Video CDN Switcher 0.1.4**（项目标识
[Greasy Fork 500213](https://greasyfork.org/scripts/500213)）。它在浏览器播放信息的
XHR/fetch 与预载对象处统一处理 DASH 视频/音频，默认保留备用地址；按语言选默认
固定主机，也允许持久保存用户指定主机。它没有实时测速、熔断、媒体同一性验证或
播放器缓冲反馈，因此不能把语言到 CDN 的映射当作当前网络的性能证据。

采用“在播放信息中处理完整音视频候选、保留独立备用线路、尽量少介入播放”的思路。
不移植浏览器 hook，不按界面语言判断地理位置，不复制源码或将其无许可证实现打包。
新实现基于本仓库现有 JSON/gRPC 处理器独立编写。

## 已确认的代码风险与更改

| 原行为 | 可以复现的风险 | v3.13 行为 |
| --- | --- | --- |
| 媒体请求根据 v9 表回到保存的目标 URL | 播放器从失败目标退回原主/备用地址时，可以被再次送回同一目标；快进请求可能携带先前主机的条件校验头 | 模块不再注册媒体请求脚本；旧 `bilibili-cdn-route.js` 运行入口也只 `$done({})` |
| 无样本就提升 Akamai | 不知道当前线路与 Akamai 谁更快，更不知道当前对象是否遇到局部故障 | 无合格证据时保留服务器原主地址 |
| 两个公开视频测速后允许拼接其他视频的 hostname | 性能采样不能证明其他对象的签名、文件、缓存版本也等价 | 所有 CDN 都只允许当前响应已有的完整 URL，不拼接域名 |
| 备用候选只要求同类型媒体域 | 异常载荷中其他路径/清晰度的备用 URL 可被提升 | 自动和固定模式都要求主/备媒体路径一致；不同路径保留给播放器，不擅自提升 |
| 原主线路不总参加后台比较 | 可能只测候选，错过更好的默认服务器 | 原主地址始终参加可用候选计划，最多五个实际候选 |
| 后台只取视频轨道 | 音频 bucket 永远没有自己的证据 | 成对轮换普通视频、音频、高码率视频；包括可用 Dolby/FLAC 音频，缺少目标类型时使用实际可得轨道 |
| 每两小时才有一次学习机会 | 两个独立对象确认需要很久 | 初期最多六轮，正常完成前五轮十分钟后可再学；然后遵守 2–72 小时配置 |
| 后台探测可能遇到起播时段 | 同时下载 Range 会占用带宽 | 识别到播放信息候选后记录活动时间，三分钟内暂停新测速；30 秒内最多写一次 |

v10 主机统计格式继续使用，旧统计只有在当前响应确实提供该主机的同路径 URL 时
才影响候选选择。健康原主线路作为本次选择基准，候选须超过切换阈值才提升。
未知的新 Bilibili 媒体主机可以在严格 Range 内容验证后积累统计，不依赖静态主机名单。

默认播放路径不读取或写入 v9 的完整签名 URL 表。历史纯函数保留用于旧状态的
兼容诊断及绑定校验测试，发布脚本入口不调用它们。旧安装必须更新模块和脚本缓存，
并退出 Bilibili 再打开，避免继续使用旧脚本或已解码的缓冲状态。

## 快进与音画保护边界

仅切换 CDN 主机本身不必然造成音画不同步。问题需要结合媒体文件的一致性、
初始化与索引范围、播放器重试和解码状态判断。
[HTTP Range/If-Range](https://www.rfc-editor.org/rfc/rfc9110.html#name-range-requests)
针对具体表示的字节范围与校验条件；[DASH 时间模型](https://dashif.org/Guidelines-TimingModel/)
说明索引、初始化范围和共同时间线对轨道播放的作用。

本次保持视频、音频、Dolby/FLAC 的表示 ID、编码、带宽、SegmentBase、初始化范围、
索引、时长、字幕和未知 protobuf 字节；不调整播放进度或人为设置音画偏移。
候选提升后保留原主与其余备用 URL；媒体 Range、If-Range、Host、scheme 和 query
均由播放器使用其选中的完整 URL 发起，插件不再另行改写请求。

后台活动保护只能观测到播放信息响应，无法知道无 API 请求时长视频是否仍在播放。
初期学习会增加流量：成功按 Range 返回时，每轮通常最多约 3.4 MiB，不含 API、协议
开销和失败响应/重试。每个网络最多六次加快学习机会；失败仍退避。流量有限时可关闭
后台测速。不能据此承诺消除网络拥塞或修复 App 自身解码器故障。

## 验证

- 新增 `test/bilibili-playback-stability.test.js`：最初九项在旧实现复现失败，随后
  补充活动保护、网络隔离和六轮学习上限，共十一项专项测试。
- 旧测试中“无条件提升 Akamai”“主机 alias 注入”“发行模块必须包含媒体请求路由”
  的产品假设已更新；未跳过测试。旧状态绑定和严格 Range 验证仍保留。
- `npm run check:all`：核心 **224/224**，站点 **4/4**；确定性构建、站点 lint
  和生产构建均通过。JSON 与 gRPC 跨路径候选、媒体重试/快进/HEAD/If-Range、
  原备用回退、索引及音频时长保留均有回归断言。
- 匿名实网使用新版后台算法：两个实际候选，四次 Range 请求全部返回 206 并通过
  单响应范围/长度/内容类型校验，整轮 5563 ms，结果 `completed`；第一次采样
  不直接晋升主机，继续等待独立对象证据。

## 更新后的设备验收

1. 更新到 v3.13.0，确认模块中没有 `Bilibili CDN Cached Media Route`，只启用一个变体。
2. 保持 `CDN=auto`、`测速方式=cron`，完全退出 Bilibili 后重新打开。
3. 对此前出问题的视频固定网络和清晰度，测试连续播放、前跳/回退十次、倍速切换和
   清晰度切换；分别记录花屏、音画偏移、缓冲次数和首帧等待。
4. 如仍有异常，用同一个 Enhanced 模块仅改 `CDN=off` 对照，保留去广告设置，
   区分 CDN 选择与其他处理。需要时提供脱敏的 API host/path、当前主备 host、状态码
   和 Range/Content-Range，不分享账号 Cookie 或完整签名 URL。

发布状态以 GitHub Release、main 固定更新地址和原 Site 为准；本审计不代替真机结果。
